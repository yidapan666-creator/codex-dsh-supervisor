# Codex DSH Supervisor

Use the `dsh_*` MCP tools to supervise one DSH root session.

## Start the visible session

1. Before the first tool call, give the user a compact launch contract: whether this is a new or reused Root, the selected Standard/PTC mode and brief reason, absolute cwd, writer/read-only mode, the user-requested budget or deployment-default/unspecified state, pre-authorized direct-child cap, and the promise to open DSH Web. Do not respond with only implementation-health claims or ask the user to manually reproduce the MCP protocol. Then call `dsh_start_or_connect`. When creating a session, always pass the user's target project as an absolute `cwd`; the gateway resolves it and rejects a missing, nonexistent, non-directory, or relative path so the DSH Web session opens on the intended files. Select the durable agent preset once at creation: use `standard` by default for ordinary implementation, debugging, review, or interactive work; use `code` (DSH Web's PTC mode) when a new session's task is dominated by broad repository exploration, independent reads/searches, or multi-step routine tool sequences that benefit from batching. Do not ask the user merely to choose between these two when the task makes the tradeoff immaterial; state the selected mode in the start update and honor an explicit choice. `minimal` is not eligible because its reduced stack cannot guarantee the supervised read-only boundary; `cordis`/Creator is not eligible because it can modify the Host runtime and preset compositions. The gateway fails closed on unqualified custom presets. It connects to the configured Host, or starts one when `DSH_HOST_LAUNCH` is explicitly configured (automatic Host startup never happens without it). Pass the existing `sessionId` to reconnect and reuse the same session; omit `cwd` and `agentPreset` unless verifying the same values, because reconnect preserves both and rejects a conflict. A session that has produced work cannot switch preset; start a separate Root if a different mode is genuinely required. Treat the returned `agentPreset` as authoritative. The Host remains independently owned and MCP restart never stops it. Treat the returned `sessionId` as the durable conversation address, not as one task execution.
2. Open the returned `browserUrl` in a visible browser tab so the user can watch the live session (the DSH web UI), and keep that tab available for the duration of the task. Its fragment carries the local Host credential without sending it in the initial HTTP URL; treat it as a local secret, never log/share it, and never pass it back as `hostBaseUrl`. If a tab is already authenticated for that Host, reuse it. After queuing the task, select its human-readable objective in the Web session sidebar when the UI exposes it; otherwise leave the session list visible and tell the user the `sessionId` and `runId`. MCP never owns or closes the browser.

## Assign and observe

First-wait cursor rule: record `initialWaitAfterAsOfSeq` from the `dsh_task` receipt and pass it as `afterAsOfSeq` to the first `dsh_wait`. It is the exact durable admission boundary. `observedAsOfSeq` is diagnostic and may already include early worker progress, so never use it as the first-wait lower bound. After the first wait, carry each observation's `asOfSeq` into the next `afterAsOfSeq` as usual.

### Compile one efficient execution brief

Before `dsh_task`, translate the user's request into one bounded `executionBrief`; do this inside the current Codex reasoning turn, never by making another planning-model call. Extract outcomes rather than copying the user's sentence order. Produce 1–5 cohesive workstreams:

- group work that shares files, state, or a public interface so children do not create avoidable merge conflicts;
- use `dependsOn` only for real ordering constraints and keep the graph acyclic;
- mark a workstream `child_candidate` only when its investigation, review, testing, or localized implementation can be completed and reported independently; mark shared-interface, cross-cutting, conflict-resolution, and final integration work as `root`;
- give each workstream observable `doneWhen` conditions and only compact `scopeHints`/`evidenceToGather`, never raw chat history, reasoning, logs, diffs, or tool output;
- put cross-stream interface reconciliation, integration, final verification, and handoff duties in `integration`.

The brief is a work map, not authority: `allowedScope`, constraints, budget, and approval policy remain binding. Send all workstreams in one `dsh_task` to one Root; DSH Root decides whether each `child_candidate` actually deserves a child and owns integration. Omit `executionBrief` only when the task is genuinely atomic, which records an explicit `SINGLE_STREAM_FALLBACK`. Multiple supervised Roots are not a substitute for this decomposition: use them only for independent read-only work or independent writer worktrees.

3. Before assigning a writer task, inspect `HEAD` and `git status` only to report pre-existing user changes; never commit, stash, reset, discard, or overwrite them merely to manufacture a baseline. The Host independently captures and fsyncs the authoritative Git baseline inside writer admission before the provider can run. Writer `allowedScope` values must be concrete workspace-relative path prefixes (`.` means the full session cwd), never prose or absolute/traversing paths. A completed handoff is rejected if task-era changes escape them. Read-only tasks do not require Git.
4. Mint one UUID `requestId`, then call `dsh_task` with that id, the `sessionId`, the compiled `executionBrief`, and a self-contained objective plus any task-specific context, path-prefix scope, constraints, acceptance, verification, escalation conditions, observational Git summary, and pre-authorized child budget that are genuinely known. Do not force the human to restate generic supervision rules: the gateway's deterministic `engineering-v1` instruction compiler fills missing safe engineering defaults, full-workspace `.` scope for a writer, focused-then-full verification, material-only escalation, and a Host-enforced maximum of 5 direct children. Explicit caller values—including a zero-child cap or narrower scope—always replace those defaults, and the compiler makes no extra model call. Reuse the exact same `requestId` only when the dispatch result was lost or ambiguous; Host-side atomic admission returns the durable receipt and must not queue the objective twice. A changed task gets a new request id and must wait until the session is idle. Confirm the task receipt reports the same `agentPreset`, `instructionProfile=engineering-v1`, and the expected execution-brief source/workstream ids. In PTC mode, nested SDK calls are folded from DSH's durable `tool/code-dispatch*` events, so handoff validation, progress tool counts, project activity, and uncertain-effect recovery retain the same semantics as Standard. Default to `writer`; choose `read_only` for analysis. Pass `tokenBudget.maxTokens` when the user chose a limit; otherwise let the deployment's `DSH_DEFAULT_TASK_TOKEN_BUDGET` apply when configured. Token budget means a Host-enforced provider-token cutoff over uncached input + cache read/write + output, never an estimated money conversion or an exact billing cap: request preflight fsyncs estimated input and capped output in a Host-private ledger before dispatch, then removes the reservation only after provider usage is durably checkpointed. Record the returned `runId`: every wait, answer, steer, cancel, child-observation, and interrupt call for this execution must carry the exact `sessionId + runId`. A second writer needs an independent Git worktree, not a workspace lock service.
   Treat ordinary in-scope edits, focused compilation/tests/builds, routine debugging, and any explicitly pre-authorized child use as execution authority: do not ask the human again. Escalate only when a missing choice would materially change the requested result, or before a security-sensitive, destructive, credentialed, external, or otherwise unauthorized side effect.
5. Call `dsh_wait` with the exact `sessionId + runId` and default timeout (300000 ms) — the five-minute aggregated progress cadence. One long observation arrives about every 300000 ms; do not re-poll on ordinary event churn. Return timing is controlled by the observation's explainable `decision`: locked protocol boundaries and policy-matched worker requests may be immediate; ordinary progress stays in the cadence. Follow `decision.action` and `decision.audience`; do not ask the human when the result says cadence/none. A `WAITING`/`TIMEOUT` return is the cadence observation: aggregate `progress` since the prior `asOfSeq` — step delta, tool counts by name, token deltas, and compact `projectActivity` (distinct files touched by successful edits/writes and targeted verification commands like `pnpm verify`) — plus the latest accepted bounded `supervisorProgress` milestone when present. Surface the compact summary to the user; never dump raw reasoning, logs, diffs, tool arguments, or tool outputs. Carry the returned `asOfSeq` into the next `afterAsOfSeq`; it is only an observation cursor, never a server resume cursor. A stale-run failure means a newer run exists: do not act on it as though it belonged to the old execution.
   `decisionShadow`, when present, is observer-only evidence. Report a material behavioral difference for later policy review, but never act on the shadow timing/audience/action during the current run.
6. Resolve `APPROVAL_REQUIRED` and `QUESTION_REQUIRED` with the matching answer tool, exact `sessionId + runId`, and the current observation's stable `rpcId`; never answer a replayed/stale interaction id. If either interaction carries `answerInWeb=true`, its payload exceeded the bounded supervisor envelope: tell the user to resolve the full interaction in DSH Web and do not call an MCP answer tool with the truncated preview. For `SUPERVISOR_REQUIRED`, surface the bounded milestone, risk, and requested next action; steer only when the answer follows from the user's already stated policy, otherwise ask the user. Use `dsh_steer` only to transmit explicit user-authored new guidance or a user-requested correction; never synthesize a nudge merely because progress paused or a child settled. Use `dsh_cancel` only for the active run. After a checkpoint, continue by queueing a new run with `parentRunId`; do not use a free-form steer as a continuation protocol.
7. Distinguish `WAITING.wait.reason=TIMEOUT` (cadence window expired) from worker state, and inspect `workerState` separately. For `FAILED`, report the explicit failure kind.
8. Accept success only from `COMPLETED`. The runtime requires a valid Root `supervisor_handoff` result, its corresponding `turn/end`, and convergence of every affiliated child. A turn ending alone is `MISSING_HANDOFF`. An early Root handoff remains `WAITING/children-running`; after the last affiliated child reaches a durable terminal boundary it becomes `WAITING/root-rehandoff-required` until Root integrates the child results and publishes a strictly newer valid handoff plus turn end. `dsh_runs`, `dsh_recover`, and `dsh_wait` all apply this same completion rule. A child's durable `token-budget-exhausted` boundary overrides an older completed Root handoff and is an enforced stop, not completion. A `dsh_runs` entry may carry `budgetWarning` when the read-only budget projection is temporarily unavailable; the run identity and convergence status remain discoverable. Report `budget` with its explicit coverage: ordinary root observations can show only `root_session`, while the Host enforcement and an exhausted terminal boundary cover the `run_tree`; spawn/fork/nested/reused-child affiliation is derived from existing durable lineage and accepted-work facts with no extra model call. Request preflight prevents concurrent allowance oversell and caps output, but provider-reported totals can still cross the cutoff by input-token estimation/provider-reporting variance; do not describe it as an exact billing cap. Treat `usageMonitor` as optional session-level cross-check data only—never as budget authority. Terminal reporting must recap steps, tool counts, token deltas, verification results, the worker's final files, and the computed `projectActivity` totals. State whether activity coverage is complete or partial and distinguish runtime-correlated verification evidence from worker claims; never equate every tool call with a project change. Also report whether `journal.recorded` succeeded. The journal uses existing runtime facts and zero additional model calls; its warning never changes the task outcome. Do not retrieve historical records unless explicitly requested or selected by a future retrieval policy.

## Reconnect and continuation

If Codex or MCP disconnects, do not replay the task: the independently owned Host and session continue. `dsh_recover` always requires the exact `sessionId + runId`; when both are known, call it directly and continue `dsh_wait` from the returned `asOfSeq`. When identity was lost, call read-only `dsh_runs`, select the matching durable run, then call `dsh_recover`. A stale recovery is a protocol failure and never means `REATTACHED`. If dispatch itself was ambiguous, retry `dsh_task` with the original `requestId`; never mint a second id for the same dispatch attempt.

If recovery returns `CONTINUATION_REQUIRED`, the Host restarted and durably closed the in-flight turn as interrupted. It also returns a runtime-generated `recoveryCapsule` capped at 16 KiB and folded across the complete affiliated run tree. Queue a new bounded `dsh_task` with `parentRunId` set to the interrupted run, a fresh `requestId`, and that exact capsule; either field without the other is invalid. Admission refreshes Host history and recomputes the capsule, so never edit, summarize, or reconstruct it. If `uncertainEffects.total > 0`, report the uncertainty and require the worker to reconcile each session-scoped entry before retrying it; an entry means a possibly side-effecting call had no durable correlated result, not that the effect definitely occurred. Never reconstruct tool arguments, blindly replay an unresolved call, infer success from the interrupted `turn/end`, or repeat the full old prompt. Missing, fabricated, stale, cross-session, and child-incomplete capsules are protocol/recovery failures, not permission to continue.

## Children

When the user has pre-authorized up to 5 direct DSH children for the task, record that limit in the task authority and delegate freely within the cap without asking again. The Host atomically enforces `maxDirectChildren` from durable session creation facts plus in-flight start reservations across both bundled child-start tools; DSH's native `maxDepth: 1` permits Root-to-child delegation and forbids grandchildren. Do not implement a second cap in Codex and do not turn an over-limit denial into a human approval request. DSH root exclusively owns child orchestration: the Host automatically relays child reports and settled notices into the root session. `dsh_agents` with the current `sessionId + runId` is read-only observability and excludes historical children not affiliated with that run — report child activity and telemetry to the user, but never relay child completion/results with `dsh_steer`, never wake root to "take over," never steer or re-prompt a settled child, and never infer authority from observing one. Use `dsh_interrupt_agent` only on an explicit human request or a clear safety/resource emergency; the runtime rejects historical, non-affiliated, and non-continuable targets.

## Compile and verification policy

Run the narrowest relevant verification after a coherent or high-risk edit batch (for example, one focused test file or a single package typecheck), not after every edit. Run full verification (`pnpm verify` or the task's declared verification commands) before handoff, and report its results in the handoff `verification` array. Do not report raw logs; report compact outcomes.

## Boundaries

Never stop the DSH Host when the MCP task ends. On MCP restart, reconnect to the configured Host and the same session id. Verify artifact hashes and paths from the returned manifest before relying on them.

Worker handoff summaries stay at or below 2048 characters, and the file list, verification claims, blocker/failure fields, hypotheses, and artifact list must remain within the bounded tool schema; detailed task reports arrive as admitted artifacts under `.dsh-handoff/<runId>/` inside the session cwd (gitignored; legacy v1 packets may use taskId). Do not treat an over-limit field as a failure to report detail — the worker should compact it and pass the report path in `artifacts`. If an observation carries `handoffTruncated`, tell the user which malformed or legacy fields MCP defensively bounded and rely on admitted artifacts for full detail.

Keep authority separated: DSH handles safe local execution, Codex decides material engineering or architecture changes, and the human decides security-sensitive or external side effects.

If the Host cannot be reached, report that connection failure. Do not silently start a Host unless `DSH_HOST_LAUNCH` was explicitly configured.
